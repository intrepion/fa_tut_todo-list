# Spec

Build a Todo List API that uses HTTP JSON routes and persists task resources in SQLite.

## Goal

Build a small project app that introduces:

- adapter-owned JSON over HTTP routes
- database-generated numeric task ids
- durable SQLite persistence
- test-first service and adapter logic
- thin adapters

## Canonical Resource Shape

Every tutorial run for this path should treat the task resource as:

```text
id: integer
text: string
```

A fresh SQLite database should create ids in increasing numeric order beginning with `1`.

## Core Logic Contract

The shared contracts for this path are:

```text
list_tasks() -> task[]
create_task(task_text: string) -> task
get_task(task_id: integer) -> task | not_found
delete_task(task_id: integer) -> deleted | not_found
```

Canonical behavior:

- blank or whitespace-only task text is rejected
- task ids are generated by SQLite when rows are inserted
- `GET /api/tasks` returns all tasks ordered by id ascending
- `POST /api/tasks` creates one task and returns the created task resource
- `GET /api/tasks/:id` returns the matching task resource or `404`
- `DELETE /api/tasks/:id` deletes the matching task resource or returns `404`

Examples with a fresh database:

- `POST /api/tasks` with `{"text":"Buy milk"}` returns `{"id":1,"text":"Buy milk"}`
- `GET /api/tasks` returns `{"tasks":[{"id":1,"text":"Buy milk"}]}`
- `GET /api/tasks/1` returns `{"id":1,"text":"Buy milk"}`
- `DELETE /api/tasks/1` returns `204 No Content`

## Non-Goals

This path does not include:

- authentication or authorization
- task editing
- due dates
- priorities
- categories or tags
- multiple lists
- syncing tasks across machines

## Surface Expectations

For this path, the API adapter should expose these canonical routes:

- `GET /api/tasks`
- `POST /api/tasks`
- `GET /api/tasks/:id`
- `DELETE /api/tasks/:id`

The adapter should keep request parsing, route handling, and SQLite wiring thin, and it should delegate task validation and not-found behavior to the code layer.

## Testing And Coverage Contract

Minimum test expectations:

- a test that blank task text is rejected
- a test that tasks are listed in id order
- a test that the first created task in a fresh database gets id `1`
- a test that missing ids return `404`
- tests for every adapter built in the chosen run that prove it returns `201` for create, `200` for list and fetch, and `204` for delete
