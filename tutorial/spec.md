# Spec

Build a Todo List API that uses REST-style JSON routes and persists task resources in Postgres.

## Goal

Build a small project app that introduces:

- resource-oriented task routes
- database-generated UUID task ids
- durable Postgres persistence
- `sqlc`-generated Go query code
- test-first service and adapter logic
- thin adapters

## Canonical Resource Shape

Every tutorial run for this path should treat the task resource as:

```text
id: uuid string
text: string
```

A fresh Postgres database should create a new UUID string every time a task row is inserted.

## Core Logic Contract

The shared contracts for this path are:

```text
list_tasks() -> task[]
create_task(task_text: string) -> task
get_task(task_id: uuid string) -> task | not_found
delete_task(task_id: uuid string) -> deleted | not_found
```

Canonical behavior:

- blank or whitespace-only task text is rejected
- task ids are generated by Postgres as UUID strings when rows are inserted
- the Postgres adapter uses `sqlc` to generate its CRUD query package from checked-in SQL files
- `GET /api/tasks` returns all tasks ordered by text ascending, then id ascending
- `POST /api/tasks` creates one task and returns the created task resource
- `GET /api/tasks/:id` returns the matching task resource or `404`
- `DELETE /api/tasks/:id` deletes the matching task resource or returns `404`

Examples with a fresh database:

- `POST /api/tasks` with `{"text":"Buy milk"}` returns `{"id":"11111111-1111-1111-1111-111111111111","text":"Buy milk"}`
- `GET /api/tasks` returns `{"tasks":[{"id":"11111111-1111-1111-1111-111111111111","text":"Buy milk"}]}`
- `GET /api/tasks/11111111-1111-1111-1111-111111111111` returns `{"id":"11111111-1111-1111-1111-111111111111","text":"Buy milk"}`
- `DELETE /api/tasks/11111111-1111-1111-1111-111111111111` returns `204 No Content`

## Non-Goals

This path does not include:

- authentication or authorization
- task editing
- due dates
- priorities
- categories or tags
- multiple lists
- syncing tasks across machines

## Surface Expectations

For this path, the API adapter should expose these canonical routes:

- `GET /api/tasks`
- `POST /api/tasks`
- `GET /api/tasks/:id`
- `DELETE /api/tasks/:id`

The adapter should keep request parsing, route handling, and Postgres wiring thin, and it should delegate task validation and not-found behavior to the code layer.

## Testing And Coverage Contract

Minimum test expectations:

- a test that blank task text is rejected
- a test that tasks are listed in stable order
- a test that created tasks receive non-empty UUID ids
- a test that missing ids return `404`
- tests for every adapter built in the chosen run that prove it returns `201` for create, `200` for list and fetch, and `204` for delete
